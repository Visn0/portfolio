01 / protein analysis

A protein analyser with no server on the critical path

Paste a sequence, a UniProt accession, an Ensembl protein ID, or import a FASTA, GenBank, GFF3 or PDB file. You get composition, molecular weight, isoelectric point, aromaticity, a feature map, a hydropathy profile and — when the record has a structure — an interactive 3D cartoon.

The design decision underneath everything

Browser WebAssembly cannot issue HTTP requests cleanly, so the split is network in TypeScript, compute in Rust. But the Rust core is not a parsing helper: it decides which URLs to request and how to interpret the responses, so the interesting logic is still testable Rust with no browser in sight. Because UniProt and Ensembl both answer cross-origin requests, the browser calls them directly — open the app and it works, with nothing to deploy on the path that matters.

Honest failures, and one deliberate refusal

  • An unreachable API, an unparseable file, a DNA sequence or an identifier outside the protein namespaces each produce a card that names the problem, rather than a spinner that never ends.
  • Nucleotide input is refused with an explanation rather than quietly translated — this is a protein tool and it says so.
  • Annotations are read from the coordinate file it already downloaded: declared sites, named mutations, bound molecules, modified residues, chain ends and disulfides as a line between their two sulfurs. No second request. A label whose residue is behind the protein is hidden instead of drawn through it.

Two renderers, so hardware acceleration is optional

The structure view extrudes a smoothed backbone as a tube — round and thick for helices, wide and flat for strands, thin for loops, coloured by secondary structure. WebGL is used when the browser offers it; the same mesh, lighting and depth cueing are rasterised on the CPU when it does not, so a browser with hardware acceleration switched off still gets a picture.

Testing and deployment

  • Rust domain tests for parsers, statistics, properties, identifiers and provider planning; a separate suite for the 3D library.
  • Headless Node checks over the WebAssembly ABI, the API layer, 3D maths and the built bundle — no browser, no network.
  • A Playwright suite drives the built app in real Chromium.
  • One wrangler deploy: a Cloudflare Worker serves the static bundle and answers /api/* itself, so the free plan is enough. CI runs the core, worker, library and web jobs before it deploys, then reads the deployed URL back to confirm the three pages and the WebAssembly binary match what was uploaded.

Not built yet

BLAST. The relay for it exists and is tested, but no control in the interface calls it — so it is not on this page as a feature.

02 / KV-cache compression

Cutting the KV cache in half without losing the model

An implementation of TurboQuant (arXiv:2504.19874, ICLR 2026) integrated into vLLM and benchmarked on real hardware — a single RTX 5090 running a dense 27B model, and eight RTX 3090s running a pruned mixture-of-experts model with 205 experts.

The idea, in one paragraph

Keys are compressed with a (b−1)-bit MSE quantiser plus a one-bit QJL residual; values use grouped quantisation with per-group scales and zeros. The most recent tokens stay uncompressed in a ring buffer, so decode reads compressed history plus a full-precision recent window. Only the full-attention layers are compressed — the linear-attention layers are left alone.

On the 5090 the same change freed 30.0 GB across four GPUs and doubled the maximum token capacity from 457,072 to 914,144. Prefill rose 5.7 % and decode 3.1 % at 30k context — compression that also made it slightly faster, rather than a trade of speed for memory. Needle-in-a-haystack retrieval held at 4/5 across every context length up to 131k in the baseline run, and the one miss is the model reformatting an answer, not a retrieval failure.

How it is wired in

  • The compressed representation is described as C++ structures to add to the runtime: encoded keys (packed MSE indices, packed QJL signs, residual and original norms), encoded values (packed groups with scales and zeros) and a per-layer cache holding compressed history plus the recent ring buffer.
  • The patch order is deliberately incremental: capture compressed K/V while still running baseline attention, then a hybrid read path for decode only, then the full read path with quality, memory and throughput measured at each step.
  • Memory accounting and context-limit calculation had to be updated with it — a compression scheme that does not report its real footprint fools the scheduler into over-committing.

03 / cloud-lab simulation

A cloud lab you can bring up with one command

A self-contained simulation of a protein-design foundry API — browse a target catalogue, submit binder sequences as an experiment, get a cost estimate, watch it move through lab stages, pull structured results. Real wet-lab results take weeks; here a worker produces mocked but deterministic results in seconds.

The point is the agent, not the simulation

The demo exists to show how an AI agent uses a lab API over MCP — both to do the job (design a binder → submit → read results) and to find bugs in the service. Every layer maps onto the managed service it stands in for, which is why the topology is not simplified: 

frontend (Next.js) ── Vercel ──► service (mock Foundry API + MCP) ──► db (Postgres) ── Supabase
      submit / poll / results          │  on submit: enqueue                ▲
                                       └──► redis ──► worker (arq) ──────────┘  ── Modal (mock "wet lab")
opencode-agent ── designs a binder & hunts bugs via MCP ──► service /mcp        ── AI agent

Two agent modes, and CI that runs both

  • demo — the agent designs a binder and drives the full loop end to end.
  • evaluate — the agent acts as an AI beta tester: it attempts the real task and judges how well the API works for an agent. Are the tools and parameters clear, are the errors descriptive, did anything block it? It ends with VERDICT: PASS or FAIL, and CI only fails the check on FAIL.
  • Three workflows, all posting sticky PR comments: unit tests plus an image pushed to GHCR, an AI code review that posts a severity table and fails on "request changes", and the AI beta tester that brings the stack up and lets an agent use it.

The MCP tool surface mirrors the vendor's own SDK, so an agent that knows the real API transfers 1:1 — the simulation is a rehearsal space, not a lookalike.

04 / seasonal meal planner

Meal planning that starts from the ingredients Switzerland actually has in winter

A small Flask application: enter age, sex, weight, height and activity level, and it calculates daily caloric needs, then assembles balanced weekly meals from a curated seasonal-ingredient database — with a consolidated shopping list and optional AI-generated images.

What it does

  • Personalised daily targets from the profile, not a fixed table.
  • Meals composed to hit protein, carbohydrate, vegetable and fat components, drawn from a Swiss winter ingredient database and macro ranges.
  • A weekly schedule across however many days you ask for, plus one consolidated shopping list.
  • Optional images per meal through Hugging Face's FLUX.1-schnell; the token is supplied in the UI or in the environment, and image generation simply turns off when there is none.

Why it is on this page

It is the least glamorous project here and the one I use every week. It is also the smallest end-to-end slice of my day job: a service with a config surface, an external dependency that can be absent without breaking the app, and a data model that has to be sane enough to produce a shopping list a human will actually follow.
